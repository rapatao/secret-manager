# Security notes

- Without [encryption](storage.md#encryption), values are only as protected as the storage backend: Secrets in your cluster, the `file` backend's file, or the `postgres` backend's database. Set an encryption key, or enable encryption at rest in the cluster (k3s: `--secrets-encryption`), and restrict who can read Secrets in the server namespace. The encryption key is as sensitive as the admin token.
- Old values stay readable in history after they are changed or deleted. To purge a leaked value, delete the versions holding it with `history --delete` or the Web UI, see [History](history.md). Backups taken before still hold it.
- The CLI caches the secrets it reads, encrypted with a key in the OS keychain, for up to the server's `--cache-max-age` (default 7 days) or the integration's offline cache setting. Anyone who can use your keychain can read them. Disable the offline cache of integrations used on shared machines, or set `SECRET_MANAGER_CACHE_MAX_AGE=0` there.
- `run` masks secret values only where they appear verbatim in the command's stdout and stderr. The command can still write them to files or the network, or print them encoded (base64, URL-escaped). Short values such as `1` or `true` are masked wherever they appear.
- Backup files hold every value in plain text when written with an empty passphrase or `--no-encrypt`, or by the server without `SECRET_MANAGER_BACKUP_PASSPHRASE`, see [Backup](backup.md). Keep them out of git either way.
- A local vault is as strong as its passphrase, and anyone who can use your keychain, or read `credentials.json` without a keychain, can read the stored vault key and every value. The vault file is written with `0600` permissions; paths, key names and version times stay readable in it.
- The base64 vault key opens a local vault without its passphrase, whether it is stored by `servers login` (keychain or `credentials.json`) or given in `SECRET_MANAGER_TOKEN`, which never locks. Treat the key like the passphrase: keep it out of shell profiles, CI logs and images, see [Local vault](local-vault.md).
- `KEY=VALUE` arguments of `set` are visible in process listings and kept in shell history. Read values from a file or stdin instead, with `--env-file` (`-` for stdin) or `--json-file` (`-` for stdin), see [CLI](cli.md).
- With the `file` backend, restrict access to the file and its directory. Without an encryption key, values are stored in plain text in it.
- The `--file` storage path and the `--backup-dir` directory must not be writable by untrusted users. The server follows a symlink to an existing file when it writes: it writes a temporary file in the directory of the link's target and renames it over the target. A planted symlink therefore lets the server replace any file in a directory it can write. A dangling symlink is replaced by a regular file.
- With the `postgres` backend, give the server its own database user, limited to its database or schema, and connect with `sslmode=verify-full` when the database is on another host. `SECRET_MANAGER_DATABASE_URL` holds the database password.
- With the controller enabled, the server can manage Secrets in every namespace, where `SecretSync` targets live. Anyone who can create a `SecretSync` can read any path and write to any namespace unless the [sync policy](secretsync.md#sync-policy) is enabled. With `controller.enabled=false` it can only manage Secrets in its own namespace.
- Saving a sync policy that deletes target Secrets needs a confirmation bound to the previewed result: the digest covers the new policy and the list of SecretSyncs it disallows, so a stale, replayed or made-up confirmation cannot apply a different policy or a different list, and a fixed word is never accepted. Every save is also based on the stored policy it read, and fails when that policy changed.
- A SecretSync target can only be an `Opaque`, `kubernetes.io/dockerconfigjson`, `kubernetes.io/tls`, `kubernetes.io/basic-auth` or `kubernetes.io/ssh-auth` Secret, so a SecretSync cannot mint a `kubernetes.io/service-account-token`. A Secret of such a type that a SecretSync wrote before this restriction stays in place; see [Install](install.md#kubernetes) for finding and deleting it.
- The type allow-list covers only the Secret type. A SecretSync can set any label or annotation outside `secretmanager.rapatao.com/` on its targets, and other controllers act on some of them, such as Argo CD on a cluster Secret labeled `argocd.argoproj.io/secret-type`. Nothing checks those keys. Which namespaces receive such a Secret is decided by the [sync policy](secretsync.md#sync-policy)'s target namespaces, and with the policy disabled any namespace may receive it.
- With the `kubernetes` storage, a SecretSync cannot write into the release namespace a Secret named `sm`, `sm-tokens`, `sm-audit` or `sm-sync-policy`, or starting with `sm.` or `smh.`, and cannot set labels or annotations under `secretmanager.rapatao.com/` anywhere. The server also ignores or refuses Secrets that carry the SecretSync owner label, so a namespace user cannot feed it data. A target in the release namespace that uses one of these names goes `SyncFailed` and is not updated, and an `Orphan` one is deleted instead of detached when it is released, so no Secret that a SecretSync wrote keeps a server name, see [Reserved names and metadata](secretsync.md#reserved-names-and-metadata) and [Secrets the server refuses](storage.md#secrets-the-server-refuses). Still keep the release namespace out of the sync policy as a target namespace unless a SecretSync needs it.
- The sync policy can be changed by anyone with the admin token (Web UI), by anyone with a read-write integration token for `/` (API and `secret-manager sync-policy set`; tokens limited to a path prefix cannot read or write it), and by anyone who can write the `sm-sync-policy` Secret or the storage backend. The server loads it on first use and keeps it in memory, so edits made outside the Web UI and the API take effect after a restart, and a missing `sm-sync-policy` Secret reads as a disabled policy from then on. Saving through the Web UI or the API is audited, and re-checks every SecretSync at once when the controller runs; each SecretSync is checked again within its `refreshInterval`, at most 1 hour, at the latest.
- The metrics port has no authentication. It exposes no secret values, but restrict it with a firewall or a NetworkPolicy if others should not read it.
- The admin token signs in to the Web UI, which can read every value and create integrations. Keep it long and random, and rotate it by changing `SECRET_MANAGER_TOKEN` (its Secret in the chart) and restarting the server. Give every client its own [integration](integrations.md), as narrow and short-lived as it allows, restricted to the addresses it runs from when they are known, and revoke it when it is no longer used.
- Failed Web UI sign-ins are slowed down per [client address](client-address.md), counting an IPv6 address by its `/64` prefix. Without `--trusted-proxies`, every client behind a reverse proxy or Ingress shares one limit; limit sign-in attempts at the proxy too if the Web UI is reachable from the internet. Never list client ranges in `--trusted-proxies`.
- CLI login starts and requests with a code that matches no login are limited per [client address](client-address.md), apart from the Web UI sign-in limit: each counts as a failure, and a limited request gets `429` with `Retry-After`: `too many login requests from this address, try again in Ns` for a start, and `invalid or expired login code; too many failed login requests from this address, try again in Ns` for a code, which does not tell whether the code exists. A request with no code at all, as the CLI sends to check browser login support, gets `400` and is neither counted nor logged. An IPv6 address is counted by its `/64` prefix. Without `--trusted-proxies`, clients behind one proxy share the limit. Logins already started are never limited: polling a pending device login, and exchanging a code that matches a login, always work. Starts and failed code exchanges are only logged, never kept on the Audit page, so a client cannot fill it; the approval in the Web UI is audited. At most 100 logins can wait for approval, each for 5 minutes, so several addresses together can fill that room and block new logins until they expire.
- Approve a CLI login only if you started it. For a device login, check that the code on the approval page matches the one in your terminal.
